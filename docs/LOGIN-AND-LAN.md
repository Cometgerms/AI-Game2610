# 登录与五人联机

当前版本：一名玩家固定控制一个国家。可在同一浏览器开五个标签，以五位游客模拟对局；也支持同局域网的五台设备。国策与每回合策略分别保存。

## 游客试玩

1. 构建 C++ 引擎后启动 `pnpm dev`（Windows 可运行 `scripts/dev.ps1`）。
2. 本机打开 `http://127.0.0.1:5173`。分别在五个标签填写不同名字，点击「游客游玩」。不要在同一局中用同一个邮箱占多个国家。
3. 第一位创建房间，选择地图；其他四位在房间列表加入，或填写同一个八位房间码。私密房间需要密码。
4. 大厅内可选择空闲国家，五人齐后由房主开局。开局后国家锁定，上方国家栏只显示玩家状态。
5. 各自编辑国策、当回合策略和指令；草稿会自动保存，确认后等待其他玩家。五人确认后房主统一结算。
6. 条约需对方在自己的标签签署；修改条约会取消双方的回合确认。进入战报后开始下一回合。
7. 用「保存并返回」离开游戏画面。刷新原标签可恢复身份、席位与服务器草稿。游客身份保留在标签页内，关闭标签且无法恢复会失去该身份；长期游玩使用邮箱账号。

同局域网的其他设备打开大厅中显示的 LAN 地址。所有人连接同一台服务器；不要在其他设备输入 `127.0.0.1`。Windows 若询问防火墙访问，选择你信任的专用网络。当前开发服务器用于本地/受信局域网，公网发布需要独立服务器入口与 HTTPS。

## Supabase 邮箱验证码

已有专用项目即可，无需创建 SQL 表。把以下两项写进仓库根目录 `.env`，然后重启 `pnpm dev`：

```dotenv
SUPABASE_URL=https://YOUR_PROJECT.supabase.co
SUPABASE_PUBLISHABLE_KEY=YOUR_PUBLISHABLE_KEY
```

项目设置中的 publishable key 用于此处；不要填 service_role / secret key。配置仅由本游戏服务器读取，没有加入浏览器打包。SDK 已固定为 `@supabase/supabase-js@2.118.0`。

在 Supabase Dashboard 的 Authentication 中启用 Email provider，并允许新用户注册（若希望首次验证即创建账号）。在 Email Templates 的 Magic Link 模板中显示验证码：

```html
<h2>SOVEREIGN 登录验证码</h2>
<p>{{ .Token }}</p>
```

本界面采用「邮箱 + 验证码」，不依赖另一个标签中的 magic-link 回调。发送后将邮件中的代码复制回原标签即可。Supabase 默认邮件服务只能发给项目团队成员，且有严格额度；给普通玩家使用前配置 Custom SMTP。详细设置以 [官方 OTP 文档](https://supabase.com/docs/guides/auth/auth-email-passwordless) 和 [SMTP 文档](https://supabase.com/docs/guides/auth/auth-smtp) 为准。

服务器限制验证码发送与尝试频率，验证成功后签发自己的随机会话。浏览器只保存当前标签的游戏令牌；服务器仅保存令牌哈希。游客会话有效期七天，邮箱会话一天，邮箱重新验证后可用相同房间码恢复席位。

## 数据放在哪里

- 房间、席位、已保存草稿、历史与游戏会话存放于服务器 `.data/rooms.json`，已加入 `.gitignore`。
- 写入先落临时文件再原子替换；回合失败不会提交半份状态。只能运行一个服务进程读写同一文件。
- 重启服务器可恢复数据；删除这个文件会丢失房间与游戏会话。不要手动修改运行中的文件。
- 文字模板和主页国策仍保存在本浏览器的模板库；它们不等于云端账号资料。
- Supabase 本阶段只处理邮箱身份。将来需要云端档案、多实例服务时再加数据库与访问规则，当前不需要你配置 SQL。

## 验证范围

自动化测试使用本地模拟邮件提供方验证 Supabase SDK 的请求与成功/失败分支，不发送真实邮件。实际项目的邮件投递、SMTP 和验证码有效期需要填好配置后用自己的邮箱验收。游戏 AI 解析仍未接入；文字是策略上下文，实际动作使用指令卡。
